## 1. What this is

A byte-level, tokenizer-free language model for code completion / small general LLM use, built from the Byte Latent Transformer (BLT) paper, sped up at inference time with Fast-BLT's self-speculation. No concept/sentence tier — that piece was cut because it's architecturally mismatched to this use case (see rationale below).

---

## 2. Data flow

```
raw bytes
   │
   ▼
[entropy model]  ──▶  per-byte entropy H(x_i)
   │
   ▼
[patcher]  ──▶  patch boundaries (variable-length groups of bytes)
   │
   ▼
[local encoder]  ──▶  one embedding per patch
   │        (hash n-gram embeddings + local transformer + cross-attention pooling)
   ▼
[patch transformer]  ──▶  contextualized patch embeddings
   │        (the "global" model — block-causal, the expensive part)
   ▼
[local decoder]  ──▶  next-byte predictions
   │        (cross-attention from bytes into patch reps, then byte-level transformer)
   ▼
generated bytes
```

Two tiers only: **bytes** and **patches**. Everything is variable-length and dynamic at the patch level; nothing above that.

---

## 3. Module responsibilities

|Module|Input → Output|Learned?|Role|
|---|---|---|---|
|Entropy model|bytes → per-byte entropy|Yes, small, trained first/separately|Decides _where_ patches should start|
|Patcher|entropy trace → boundary bitmask|No (rule-based: threshold + monotonicity)|Turns entropy into actual patch segmentation|
|Hash n-gram embeddings|byte n-grams → embedding|Yes (embedding tables only)|Gives the model access to local byte-sequence identity without a vocabulary|
|Local encoder|bytes (+ hash embeddings) → patch embeddings|Yes|Compresses each patch into one vector|
|Patch transformer|patch embeddings → contextualized patch embeddings|Yes, largest component|Does the actual long-range reasoning, over patches not bytes|
|Local decoder|patch context + previous bytes → next byte|Yes|Expands one patch's context back into concrete bytes, autoregressively|

## 4. Why patches instead of tokens

A fixed subword vocabulary trades a fixed amount of information (frequent byte-groups) for a fixed amount of compute (one transformer step per token), regardless of how predictable that stretch of text actually is. BLT decouples this: patch boundaries are chosen _dynamically_ based on next-byte entropy, so predictable stretches (whitespace, indentation, boilerplate, repeated identifiers — all common in code) get long, cheap patches, and genuinely hard-to-predict bytes get short patches with more compute per byte. The expensive transformer (the patch transformer) runs once per patch, not once per byte — this is where the FLOP savings come from, and it's also why entropy patching should suit code particularly well: code has an unusually high ratio of "highly predictable" to "genuinely uncertain" bytes.

---

## 5. Why no concept/sentence tier

The concept tier (from the Large Concept Model paper) reasons over whole sentences instead of patches, trading fluency and short-range precision for long-document coherence and near length-independent long-context cost. That tradeoff is close to the opposite of what code completion needs:

- Completions need **exact** identifiers, punctuation, and syntax — the concept tier's own published numbers show it's specifically weak on exactly this (lower fluency scores, worse preservation of exact content, documented "fragility" on numbers/code/identifiers in the source paper's own analysis).
- Completions are usually **short** — the concept tier's efficiency advantage only kicks in on longer documents; on short inputs a token/patch-level model is already the more efficient choice.
- The concept tier is also the highest-risk, hardest-to-get-right piece (posterior collapse risk, needs its own hard attention-boundary fix to guarantee it's even used) — cutting it removes the single biggest implementation risk in the whole project along with the piece least suited to the goal.

Net effect: dropping it is a strict simplification with no real loss relative to the stated use case.

## 6. Why the two-tier attention design (local block-causal vs. block-causal)

- **Local encoder/decoder:** local block-causal attention — a byte attends to a fixed window of preceding bytes. This window is intentionally allowed to **cross patch boundaries** (patches are just a computation-grouping device, not a hard information barrier at this level) but **never cross document boundaries** (BLT §3.2). Kept small (1–9 layers depending on the encoder/decoder split chosen in Phase 5) because its job is local: turn nearby bytes into a patch vector, or a patch vector back into bytes.
- **Patch transformer:** block-causal at the patch level — a patch can attend to all previous patches in the same document, never across documents. This is deliberately the largest component, because this is where all genuine long-range reasoning happens in this architecture.
- **Cross-attention (encoder and decoder):** the connective tissue between the two tiers, implemented once as a generic op and used in two "modes" — pooling (many bytes → one patch query) in the encoder, and unpooling (one patch → many byte queries) in the decoder, with roles/masks swapped accordingly (BLT Figure 5).

## 7. Why hash n-gram embeddings matter this much

Without them, the local encoder only sees byte identity, not byte-sequence identity — it has to reconstruct "this looks like the middle of the word 'function'" purely from a handful of transformer layers with no vocabulary shortcut at all. Hash n-gram embeddings (rolling polynomial hash over n=3..8 byte windows, mapped into a fixed-size embedding table) give the model a cheap, vocabulary-free way to recognize recurring byte sequences directly at the embedding layer. The paper's own ablations (Table 8) show this is the single largest lever they found — expect the same here, and expect it to matter specifically for code, where identifiers, keywords, and common syntax patterns are exactly the kind of recurring n-gram structure this mechanism is built to exploit.

---

## 8. Why Fast-BLT's self-speculation, specifically

The local decoder is the one place left where computation is still strictly one-byte-at-a-time. Self-speculation (BLT-S) doesn't change the architecture at all — it changes only the inference loop: let the cheap local decoder draft several bytes past where it would normally stop, then do one full (expensive) verification pass to check the draft, keeping everything up to the first mismatch. Because verification is exact (byte-for-byte identical to plain greedy decoding), this is a strictly free win, no quality tradeoff, and it specifically pays off on the kind of highly predictable runs code is full of — closing brackets, repeated indentation, common idioms — where the draft will usually be right for many bytes in a row before the model finally does something less predictable.

Block-diffusion decoding (BLT-D) is the further, optional step — parallel multi-byte generation via a diffusion objective — but it requires retraining the decoder and adds real complexity, so it's a deliberate later choice, not a default.

## 9. Design invariants (don't violate these while iterating)

- Patch boundaries never cross document boundaries, at any tier.
- Every architecture knob that BLT's own ablations sweep (n-gram sizes/vocab, cross-attention placement, encoder/decoder depth split, entropy model size, patch size) is a **config value**, never hardcoded — this is what makes the ablation-improvement phase a sweep instead of a rewrite.
- Every forward op has a CPU reference implementation that stays correct and buildable, even after a CUDA implementation exists — it's the permanent ground truth for numerical correctness, not a scaffold you throw away.
- BLT-S must be provably output-identical to plain greedy decoding under the same weights — that's the whole point of the speculation being "free."
